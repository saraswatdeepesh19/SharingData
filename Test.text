# Prompt — Generate Confluence Handover Documentation from a Multi-Service Git Repository

You are a senior software architect and technical documentation engineer.

You are working inside a Git repository that contains **multiple services in a single repository (monorepo)**.

Your task is to inspect the repository and generate a **complete production-ready handover document for all services**, formatted specifically for **Atlassian Confluence**.

The final documentation must be useful to a new engineer who has joined the team and needs to understand, operate, troubleshoot, deploy, and maintain these services without depending on the original developers.

---

# 1. FIRST: Analyze the Repository

Before generating documentation, inspect the repository thoroughly.

Identify:

* All services/applications
* Service boundaries
* Programming languages
* Frameworks
* Build systems
* Package managers
* Shared libraries/modules
* Common utilities
* Infrastructure/configuration directories
* Deployment configurations
* CI/CD pipelines
* Dockerfiles
* Kubernetes manifests
* Helm charts
* Terraform/IaC
* Configuration files
* Environment files/examples
* API definitions
* Database-related code
* Message queues/topics
* Scheduled jobs
* Background workers
* External integrations
* Authentication/authorization
* Monitoring/logging configuration
* Tests
* Scripts
* Documentation already present in the repository

Do not assume that every top-level directory is a service.

Determine whether a directory is actually a deployable service/application by examining its code, configuration, build files, deployment files, and dependencies.

# 4. Service Documentation

For EVERY discovered service, generate a dedicated service section.

Use this structure:

## Service Overview

Explain:

* What the service does
* Why it exists
* What business/technical responsibility it owns
* What it does NOT own, if this can be determined

## Repository Location

Show the exact repository path.

Example:

```text
/services/payment-service
```

## Technology Stack

Create a table:

| Category        | Details |
| --------------- | ------- |
| Language        |         |
| Framework       |         |
| Runtime         |         |
| Build Tool      |         |
| Package Manager |         |
| Database        |         |
| Cache           |         |
| Messaging       |         |
| Container       |         |
| Deployment      |         |

Only populate values supported by repository evidence.

## Architecture

Explain the internal architecture.

Identify important components such as:

* Controllers
* Routes
* Handlers
* Services
* Business logic
* Repositories
* Clients
* Workers
* Consumers
* Producers
* Schedulers
* Middleware
* Configuration
* Persistence layer

Where useful, include a Mermaid diagram.

Example:

```mermaid
flowchart LR
    Client --> Service
    Service --> Database
    Service --> MessageBroker
    Service --> ExternalAPI
```

The diagram must reflect the actual repository architecture rather than being generic.

## APIs

Document discovered APIs.

Create a table:

| Method | Endpoint | Purpose | Authentication | Request | Response |
| ------ | -------- | ------- | -------------- | ------- | -------- |

Look for API information in:

* Controllers
* Routes
* OpenAPI/Swagger
* GraphQL schemas
* API specifications
* Tests
* README files

Do not invent endpoints.

## Dependencies

Separate:

### Internal Dependencies

Services from the same repository that this service depends on.

### External Dependencies

Third-party services, APIs, infrastructure, or systems.

For each dependency explain:

* Why it is required
* How it is used
* What happens if it is unavailable

## Configuration

Identify configuration from:

* Environment variables
* Configuration files
* YAML
* JSON
* Properties files
* Helm values
* Docker configuration
* Kubernetes configuration
* Deployment manifests

Create:

| Variable / Configuration | Purpose | Required | Default | Example | Secret? |
| ------------------------ | ------- | -------- | ------- | ------- | ------- |

NEVER expose actual secret values.

If a secret exists in the repository accidentally, do NOT reproduce the value.

Instead write:

`SECRET: Value intentionally omitted`

## Database / Storage

Document:

* Database type
* Connection mechanism
* Schema/migrations
* Tables/entities
* Important relationships
* Read/write behavior
* Caching
* Data retention if discoverable

Do not expose credentials.

## Messaging

If applicable, document:

* Broker
* Queue/topic names
* Producer behavior
* Consumer behavior
* Message format
* Retry behavior
* Dead-letter handling
* Important failure scenarios

## Scheduled Jobs

Identify:

* Cron jobs
* Scheduled tasks
* Workers
* Batch processes
* Queue consumers

Document:

| Job | Schedule | Purpose | Service | Failure Handling |
| --- | -------- | ------- | ------- | ---------------- |

## Logging & Monitoring

Document:

* Log framework
* Important log messages
* Log levels
* Correlation/request IDs
* Metrics
* Traces
* Health endpoints
* Readiness/liveness checks
* Monitoring configuration
* Alert configuration

## Build & Run

Provide exact commands discovered from the repository.

For example:

```bash
# Install dependencies
...

# Build
...

# Run
...

# Test
...

# Lint
...
```

Do NOT invent commands.

Use commands from:

* package.json
* Makefile
* Gradle
* Maven
* pom.xml
* build scripts
* Dockerfile
* README
* CI configuration
* repository scripts

## Deployment

Explain:

* How the service is packaged
* Containerization
* Image creation
* Deployment manifests
* Kubernetes resources
* Helm charts
* Environment-specific configuration
* CI/CD pipeline
* Deployment order
* Rollback process

## Troubleshooting

Create a practical troubleshooting table:

| Problem | Possible Cause | How to Diagnose | Resolution |
| ------- | -------------- | --------------- | ---------- |

Only include issues that can be inferred from code/configuration/history/documentation.

Clearly distinguish repository evidence from reasonable operational recommendations.

## Known Limitations

Document:

* TODOs
* FIXME comments
* Known technical limitations
* Deprecated dependencies
* Workarounds
* Technical debt
* Potential risks

The final output must represent the document using:

```text

    ├── UI TAB
    └── UI TAB
```

For the Services section:

```text

    UI TAB: Service A

    ...
```

Do not flatten the service documentation into one long page.

Each service must have its own UI Tab.

# 13. OUTPUT FORMAT — VERY IMPORTANT

Generate TWO files:

### File 1: `confluence-handover.md`

A human-readable version of the complete documentation.

Use this syntax to make the macro hierarchy explicit:

```text
[UI TABS]

[UI TAB: System Overview]

...

[END UI TAB]

[UI TAB: Services]

[UI TAB: Service A]

...

[END UI TAB]

[UI TAB: Service B]

...

[END UI TAB]

[END UI TAB]

[END UI TABS]
```

### File 2: `confluence-handover-storage.xhtml`

Generate the equivalent **Confluence Storage Format XHTML**.

The XHTML must use Confluence macro markup for the UI Tabs/UI Tab macros.

IMPORTANT:

Do not use generic Markdown in this file.

The goal is that this file can be used with Confluence's API or a suitable Confluence import/update mechanism to create the page while preserving the UI Tabs/UI Tab macro structure.

Before generating the XHTML, determine the correct macro names and parameters used by the UI Tabs/UI Tab implementation available to this repository/team.

If the repository does not contain evidence of which UI Tabs plugin/macro is being used, DO NOT invent the macro syntax.

Instead:

1. Generate the Markdown documentation.
2. Generate a clearly marked XHTML template.
3. Add a `CONFLUENCE MACRO CONFIGURATION REQUIRED` section explaining exactly which macro information is needed.
